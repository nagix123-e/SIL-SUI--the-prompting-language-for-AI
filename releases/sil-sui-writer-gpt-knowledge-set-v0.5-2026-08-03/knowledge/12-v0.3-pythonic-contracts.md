# SIL/SUI v0.3 — Compatible Pythonic Contracts

v0.3 remains a compatible SIL/SUI syntax. New output defaults to v0.5; see `14-v0.5-ui-layers-and-continuation.md` for new UI layers and `13-v0.4-bounded-loops.md` for a bounded task loop or SUI collection template. These versions are deliberately Python-like only in layout: they are **not Python** and never contain expressions, imports, assignments, calls, or executable runtime.

## Canonical syntax and lexer

- A declaration ends with `:` and its children are indented exactly four spaces.
- Tabs, mixed indentation, orphan indents, invalid dedents, missing colons, and empty declared blocks are errors.
- `#` is the canonical line comment. `//` is accepted only when reading legacy content.
- Semantic references and IDs are English ASCII identifiers. Human copy may be quoted. Use `"""` blocks only as inert human/code-example data.
- `version: 0.3` is a language version. `revision: 4` inside `contract:` is a contract revision; never conflate them.

```sil
bundle AuthenticationFeature:
    version: 0.3

    contract:
        id: AUTH_FEATURE
        revision: 4
        status: review
        supersedes: AUTH_FEATURE@3
        compatibility: backward_compatible
        execution_authorized: false

    task ImplementAuthenticationApi:
        version: 0.3
        goal: feature.add
        target: auth.api
        action: implement
        output:
            api.authentication
        verify:
            tests.pass
        on_failure:
            task.abort
```

`execution_authorized` records a declaration only. A Runner or host must never treat it, validity, readiness, compilation, or a handoff as actual permission to use tools or edit files.

`metadata:` is also a valid declarative envelope block. Use it for source-language and normalization metadata when it is preferable to keep that provenance separate from lifecycle fields:

```sil
metadata:
    original_source_language: ja
    normalized_semantic_language: en
    output_identifier_language: en
```

`readiness:` is a declarative, producer-supplied readiness snapshot. The Runner preserves it as contract data but computes its own static readiness profile separately; it never treats a supplied `ready` value as execution permission.

```sil
readiness:
    implementation: review
    verification: blocked
    authorization: false
```

## Structured statements, IDs, provenance, and scope

The normalized v0.3 IR stores every statement as `{ id, field, reference/value, appliesTo, parentId, sourceOrder, provenance, confidence, diagnostics }`. Stable generated IDs survive canonical formatting; use an explicit ID when a later Patch will address one exact statement.

```sil
task PasswordChange:
    version: 0.3
    goal: feature.update
    target: user.password
    action: implement
    require REQ_PASSWORD_HASH:
        on user.password:
            rule: password.hash
    on_failure:
        task.abort
```

`on user.password:` scopes all child statements to that exact reference. Do not use a SemanticRef itself as an ID. Provenance is one of `user_explicit`, `user_inferred`, `defaulted`, `repository_observed`, `document_observed`, `knowledge_observed`, or `externally_verified`. A defaulted `on_failure: task.abort` must be marked `defaulted`.

## Flow and dependency DAG

Textual order does not create a dependency. Use `depends_on`, `sequence`, or `parallel`. The Runner builds a DAG, rejects unknown tasks, duplicate/self dependencies, direct or indirect cycles, empty parallel blocks, short sequences, type mismatch, and isolated contracts.

```sil
bundle Delivery:
    version: 0.3
    task BuildApi:
        version: 0.3
        goal: feature.add
        target: api.auth
        action: implement
        output: api.auth
        verify: tests.pass
        on_failure: task.abort
    task BuildUi:
        version: 0.3
        goal: feature.add
        target: ui.login
        action: implement
        depends_on:
            BuildApi
        output: ui.login
        verify: tests.pass
        on_failure: task.abort
    flow DeliveryFlow:
        sequence:
            BuildApi
            BuildUi
```

## Typed semantics, verification, rules, and data policy

Use named declarations rather than hiding values, units, schemas, permissions, or exceptions inside one dotted reference.

```sil
parameter ResponseLatency:
    type: duration
    value: 200
    unit: ms
    operator: less_than

model LoginRequest:
    format: json_schema
    field email:
        type: string
        required: true
    field password:
        type: string
        required: true

verification LoginSuccess:
    applies_to: auth.session
    method: integration_test
    command_source: repository.package_scripts
    observe: http.response
    expected: status_code.200
    evidence: test.report
    unavailable_behavior: verification.report_unavailable

rule DeleteUserPermission:
    subject: role.admin
    action: user.delete
    resource: user.account
    when:
        target.user_not_self
        organization.same
    effect: allow
    exception:
        account.last_owner

data_policy UserEmailPolicy:
    data: user.email
    classification: personal
    readable_by:
        role.admin
    writable_by:
        role.user_self
    retention: account_lifetime
    external_transfer: forbidden
    log_value: false
```

`rule` is declarative, never an executable condition. Verification execution status is independently `not_executed`, `running`, `passed`, `failed`, `environment_unavailable`, or `evidence_insufficient`; an unrun test is never passed.

## SUI component graph and binding

Nest every component below its owner. Component IDs are unique within the bundle. Bindings must use exact declared source and target identifiers, never partial-name inference.

```sui
ui LoginScreen:
    version: 0.3
    screen: login_screen
    component LoginForm:
        kind: form
        component EmailInput:
            kind: input
            bind: input.user.email
        component SubmitButton:
            kind: button
            content: "Log in"
            interaction:
                on click:
                    action.authenticate
            state:
                loading
                disabled
```

## Patch contract

Patch operations are `add`, `remove`, `replace`, `move`, `change_scope`, `change_force`, `reorder`, `add_dependency`, and `remove_dependency`. They target stable task/UI/component/statement IDs. Apply all operations to a copy, then revalidate syntax, references, graphs, binding, rules, data policy, readiness, and authorization. If any operation fails, retain the original document unchanged.

## Multilingual source policy

Detect or read the source locale, retain `originalSourceLanguage`, and normalize semantic meaning to English before producing identifiers. Store `normalizedSemanticLanguage: en` and `outputIdentifierLanguage: en`. Do not translate unknown proper nouns into guessed English; preserve them through a precise `context.*` or declared semantic extension. Do not call external translation services without explicit host configuration and permission. When an adapter is unavailable, report `adapter_unavailable` rather than fabricating normalization.

## Legacy migration

v0.1/v0.2 brace files remain readable. `sil migrate legacy.sil` emits the representable v0.3 task form. `sil format contract.sil --legacy` emits pre-v0.3 syntax only with explicit `lossy-legacy-format` warnings for scope, provenance, graph, lifecycle, Patch, or typed data that legacy syntax cannot express. Core v0.1 registrations and quantized codes do not change.
