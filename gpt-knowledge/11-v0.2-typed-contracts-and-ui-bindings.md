# SIL/SUI v0.2 — Legacy Typed Contracts, Data Models, Code Examples, and UI Bindings

> v0.3 supersedes this syntax for new output while retaining v0.2 parsing. Translate typed declarations into the indentation-sensitive v0.3 forms in `12-v0.3-pythonic-contracts.md`; do not discard values, units, models, bindings, or extension meanings.

Use v0.2 whenever a request includes typed values, numerical constraints, units, comparison operators, API or database shapes, file schemas, reusable code examples, design tokens, responsive ranges, accessibility attributes, state transitions, or a machine-checkable SIL/SUI relationship.

## Version declaration

The first statement inside every v0.2 block is `version: 0.2`.

```sil
task BuildSearchUi {
  version: 0.2
  goal: feature.add
  target: product.search
  action: implement
  output: search.results
  verify: tests.pass
  on_failure: task.abort
}
```

## Typed parameters

Use a parameter block instead of encoding values in a reference name.

```sil
parameter response_time {
  type: number
  value: 200
  unit: ms
  operator: lte
}
```

`type` and `value` are mandatory. A parameter with `unit` must also declare `operator`. Use `number`, `string`, `boolean`, `duration`, `percentage`, or another precise English type. Operators include `eq`, `neq`, `lt`, `lte`, `gt`, `gte`, `contains`, and `matches`.

## Data models

Use a model block for API input/output, JSON Schema, DB records, CSV columns, files, and other exact shapes.

```sil
model SearchRequest {
  format: json_schema
  field query {
    type: string
    required: true
  }
  field page_size {
    type: integer
    required: false
  }
}
```

Every model needs `format`; every field needs `type` and `required`. Use model names such as `SearchRequest`, `SearchResponse`, `UserRecord`, or `ImportCsv`.

## Code example declarations

Declare a code example when the task needs a concrete example in prompt context. `source` refers to an attachment, Knowledge file, repository example, or future stored sample. Use embedded code only when the user supplied it or requested it.

```sil
example SearchRequestJson {
  language: json
  applies_to: model.SearchRequest
  source: samples.search_request_json
}
```

```sil
example SearchRequestJson {
  language: json
  applies_to: model.SearchRequest
  code: """
{"query":"keyboard","page_size":20}
"""
}
```

Do not claim an example source was read unless it was accessible. Preserve code exactly; never convert embedded code into a SemanticRef.

## Portable semantic extensions

When a necessary domain term is not confirmed as a Core codebook preset, do not pretend it is registered and do not leave its meaning implicit. Declare a `semantic` block for each material unregistered reference. It may be nested in a v0.2 task/UI contract or emitted as a top-level bundle declaration; use the top-level form when several contracts share the definition.

```sil
semantic ShogiRules {
  reference: game.shogi
  kind: domain_rule
  meaning: Japanese chess rules including legal moves, captures, promotion, check, and checkmate.
  scope: bundle
}

semantic CheckmateDetection {
  reference: shogi.checkmate.detect
  kind: domain_rule
  meaning: Determine whether the side to move is in check with no legal move that removes the check.
  scope: bundle
}
```

`reference`, `kind`, `meaning`, and `scope` are mandatory. `reference` is the exact SemanticRef used elsewhere. `kind` is one of `proper_noun`, `verb`, `noun`, `domain_rule`, or `data_model`. `scope` is `bundle` when every SIL/SUI contract in the same input may use the meaning, or `contract` when it is local.

The Runner carries these declarations as a semantic extension manifest. It may report a reference as `declared_extension`, but it must never call it Core-registered or silently replace it with a guessed preset. A bundle may contain one `task`, multiple `ui` declarations, and multiple top-level `semantic` declarations in any order. Add definitions for material domain rules, data models, proper names, or custom actions; ordinary descriptive details can remain lossless extensions.

## Shared top-level v0.2 declarations

A bundle may also place reusable `parameter`, `model`, `example`, `token`, `breakpoint`, `a11y`, and `transition` blocks at top level. Use this only when the declaration is shared context rather than owned by one task or one UI contract. The Runner validates every top-level block and includes it in the generated handoff as `Shared v0.2 declarations`.

```sil
parameter board_files {
  type: file_list
  source: repository.shogi_assets
  required: true
}

model ShogiBoardFile {
  format: json_schema
  field board {
    type: array
    required: true
  }
}
```

For a shared parameter, `type` plus one of `value`, `source`, or `required` is mandatory. A top-level model, example, token, breakpoint, accessibility declaration, or transition follows the same property requirements as its nested v0.2 form.

References such as `parameter.Name`, `model.Name`, `example.Name`, `token.Name`, `breakpoint.Name`, `a11y.Name`, and `transition.Name` resolve mechanically when the matching shared declaration exists. Self-describing verification labels ending in `.pass`, `.correct`, `.complete`, `.visible`, `.responsive`, `.no_state_change`, `.matches`, or `.applies` are local acceptance labels and do not each need a semantic block. Preserve them literally; do not claim they are Core-registered.

## Evidence-backed semantic enrichment

If a Runner host explicitly permits repository, user-supplied, or Web research, it may resolve a previously unregistered reference from source-bearing evidence. This is not Core registration. The evidence must retain the exact reference, a concise meaning, the source category, and an HTTPS URL for Web evidence. A Writer GPT must never invent a URL, claim that a search occurred, or label a Web-resolved term as Core-registered.

When no source is available, write a precise `semantic` declaration or preserve the reference as an extension. Do not fabricate rules merely to make `semanticInteroperable` true.

## SIL to SUI binding

When a task output must update a visible component, emit a binding in the SIL task and ensure that the SUI block declares that component.

```sil
bind: output.search.results -> ui.SearchScreen.search_results
```

The source must be a declared `output`; the target must be `ui.<UiName>.<componentReference>` and match a `component` in that SUI block. This is a machine-checkable contract, not an instruction to update the UI immediately.

## SUI v0.2 extensions

```sui
ui SearchScreen {
  version: 0.2
  screen: search_screen
  component: search_results
  verify: render.complete
  on_failure: task.abort

  token spacing_md {
    type: dimension
    value: 16
    unit: px
  }

  breakpoint compact {
    min: 0
    max: 767
    unit: px
  }

  a11y search_results {
    role: region
    label: search_results
  }

  transition loading_to_results {
    from: view.loading
    event: request.success
    to: view.success
  }
}
```

- `token`: design token name with `type`, `value`, and optional `unit`.
- `breakpoint`: responsive range with `min`, `max`, and `unit`.
- `a11y`: accessibility declaration with `role` and `label`; add keyboard and description where material.
- `transition`: UI state change with `from`, `event`, and `to`.

This is legacy v0.2 formatting only: keep every statement indented by two spaces, nested block properties by four, and model-field properties by six. New v0.3 output uses four spaces per nesting level and no braces.
